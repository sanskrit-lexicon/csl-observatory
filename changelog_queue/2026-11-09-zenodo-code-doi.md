# csl-observatory gains its code-release DOI on every citation surface, and stops claiming it has none

**The repository now carries the Zenodo code-release DOI `10.5281/zenodo.24055368` (concept; first archived version `10.5281/zenodo.24055369`, code v1.15.0, 2026-10-29) where readers look for it: a README badge, a Quick-links bullet, the Citation section, and two `CITATION.cff` identifier rows.** Until this change the README's Citation block said plainly "no Zenodo DOI minted yet" — written before the archive existed, and stale the moment it did; the record is live on Zenodo (`resource_type: software`, GPL-3.0, creator + project contributors, `isSupplementTo` the repo), and resolves through `https://doi.org/10.5281/zenodo.24055368`. The data DOIs are untouched and keep their own scope: OBS-T concept `10.5281/zenodo.21346705`, A15 inputs concept `10.5281/zenodo.22853817` / version `10.5281/zenodo.22853818`; the Citation block now names the code DOI for software and the OBS-T concept DOI for data, so the "cite this" answer stops depending on which paragraph a reader lands in.

**`.zenodo.json` deliberately stays a dataset descriptor.** The file already describes the OBS-T deposit (`upload_type: dataset`); repurposing it for the software record would either mislabel the next data archive or silently stop archiving OBS-T. csl-atlas can point its `.zenodo.json` at software because it has no dataset deposit of its own — observatory has two releases with different scopes, so the software DOI is carried by `CITATION.cff` + README and the dataset descriptor keeps its job. Placement rule recorded in the Uprava standing policy (H7887): a repo with both a code record and a dataset record names both, each on its own surface.
